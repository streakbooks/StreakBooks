# Linkbooks competitiveness and migration review

Review date: 1 November 2026. Scope: repository inspection, public vendor documentation, automated tests, production compilation and an isolated browser test. This is an engineering and product assessment, not an independent financial audit or certification. No live accounting records were changed.

## Executive assessment

Linkbooks has a substantial accounting foundation. It is not yet demonstrated to be production-ready across every workflow or competitively equivalent to every platform below. The highest immediate switching barrier is safe migration: existing import writers needed source-column mapping, stronger previews and downloadable evidence. These improvements have been implemented, not just recommended.

The delivered migration wizard is a **single-file CSV workflow** for invoices, bills, product/service catalogues and projects. It offers source-platform selection, conservative column suggestions, manual mapping, explicit date formats, shared domain validation, existing authorized write actions, validation downloads and import outcome downloads. It does not connect to provider APIs or claim complete one-click transfer of historical books.

## Method and evidence limitations

Vendor comparisons below use primary public sources linked in each row. Product availability varies by country, edition, plan and extensions. They are capability benchmarks, not hands-on speed or usability measurements. No private vendor backend architecture is inferred from marketing. Vendor security attestations require separate scope review; missing evidence is not evidence of insecurity. Linkbooks observations distinguish code present from live behavior verified.

Existing evidence includes 150 test files / 1,130 tests passing before changes. Review focused on import definitions and preflight, invoice/bill writers, transaction retry contracts, products/projects validators, feature readiness catalog, tenant checks, accounting tests and SQL migration structure. It did not manually exercise every route, function, button, or historical migration. Public Supabase changelog retrieval through browsing returned an unsupported markdown content type; this delivery introduces no new Supabase SDK calls or schema changes.

## Implemented changes

1. `src/lib/imports/source-migration.ts`: conservative alias matching; ambiguous mappings left for review; bounded strict CSV input; duplicate/reused/stale column rejection; explicit ISO/DMY/MDY conversion; shared financial validators; formula-safe validation report exports. Transport CSV preserves contact identity rather than applying spreadsheet escaping to database input.
2. `src/components/imports/SourceMigrationWizard.tsx`: source provenance, upload, accessible field mappings, date formats, read-error handling, stale async-read protection and downloadable validation evidence. It never posts records itself.
3. `src/routes/_authenticated/imports.tsx`: integration with existing writers; stronger financial previews; organization-change state reset; pending-import module lock; downloadable outcomes including partial errors and audit failures.
4. Known foreign currency, discounts, paid amounts and tax-inclusive indicators in source transaction exports block lossy conversion. Unknown export layouts still require deliberate review; these checks are not an exhaustive vendor parser.
5. Fixed-asset feature readiness corrected to reflect existing implemented register/depreciation functionality.
6. New financial migration regression cases and an isolated Chromium browser fixture; default E2E discovery excludes the separately configured fixture.

No new database schema, direct ledger writes, provider registrations, credentials, production deploys or destructive data transformations were introduced.

## Migration controls and remaining implementation

Current sequence: export and retain originals → create/reference contacts/accounts/tax codes → select document type → upload and map → choose date format → resolve file errors → download validation evidence → import through authorized domain writer → download actual outcomes → reconcile destination to source. Known server checks resolve company-scoped accounts, contacts and effective tax codes. Imports can produce partial outcomes and saved drafts; a file validation pass is not an all-or-nothing database transaction or a completed financial reconciliation.

The source dropdown identifies provenance, not a certified provider connector. Xero-like column aliases are covered by tests; no real vendor tenant export fixtures were available. CSV only, one file at a time; no ZIP, spreadsheet, MYOB tab-delimited or direct OAuth extraction. Transaction writers support a maximum of 250 lines per file. Product types and tax codes must use destination meanings, reviewed explicitly. Attachments, invoice discounts, foreign currency, credits, payments, opening balances and allocation history are not carried by this line-import contract.

To deliver true one-click migration, implement a persisted, tenant-scoped migration job model with immutable manifests, checksums, source IDs and adapter versions; encrypted provider OAuth/token storage; source-entity mapping and full dependency graph; dry-run reference resolution; resumable server workers; unique idempotency keys enforced in Postgres; explicit cutover date and accounting basis; pre/post trial balance, AR/AP, tax, cash and stock reconciliation; exception review and a signed completion report. Define rollback as reversal/compensation, never deleting posted history. Do not import both opening control balances and the same open documents without balancing the conversion journal.

## Release blockers and priorities

- **P0 — financial integrity:** credentialed database tests for posted immutability, closed periods, duplicate import races, exact retries, partial authorization failure, tax and FX; source/destination reconciliation fixtures. Release gate: zero unexplained monetary differences in minor units.
- **P0 — security:** deployed RLS/RPC/storage matrix with two tenants, low-privilege members, revoked users and AAL1/AAL2 sessions. Confirm credential rotation, secret isolation and webhook signature/replay behavior.
- **P1 — migration:** durable jobs and provider connectors for Xero, QBO, Zoho and MYOB first. Provider access scopes, approval requirements and API limits must be verified before connector launch. Expand only with real anonymized export fixtures and reconciliation evidence.
- **P1 — operations:** restore drill, recovery targets, monitoring, failed-job queue, notification/email delivery checks, and production-like performance test. Baseline latency and throughput before setting measurable service objectives.
- **P1 — workflow completeness:** credentialed UI inventory of each route/action against permissions and error states. Existing isolated tests cannot certify all application buttons.
- **P2 — competitive breadth:** inventory valuation/COGS, sales orders, time-to-billing, retainers, pricing, consolidation/intercompany and advanced revenue recognition require distinct specifications and accounting acceptance tests. Avoid turning on unimplemented modules.

## CFO / finance release decision

Do not represent current results as universal GAAP/IFRS or tax compliance. Choose supported launch jurisdictions, accounting bases, entity sizes and required filings; obtain jurisdiction-specific accounting review. Model operating cost per active company from database load, storage, email, bank feed fees and support/migration effort. Migration conversion discrepancies and manual exception costs should be tracked alongside activation and retention. Do not invent a budget or provider pricing without measured usage and quotes.

A production-readiness claim requires the P0 gates plus operational evidence. This review delivers code and verified migration improvements while recording the unfulfilled broader requirements explicitly.
