# Firm & Clients — onboarding planning and reminder rollout

## Scope
Firm-owned operational checklists only. Existing client books, journals,
company access grants, engagement contracts and completed checklist notes are
not modified by this migration.

- Per-checklist-step `assignee_id`, `due_date`, `depends_on_task_key` and
  `reminders_enabled`.
- A single prerequisite per step, validated within the same firm and linked
  client. Cycles are rejected by the database; a step cannot be completed until
  its prerequisite is complete. Reopen completed children first.
- Staff assignment requires **both** firm membership and active membership in
  the selected client organisation. Only firm administrators can change plans.
- Custom templates support `due_in_days` (0–365, nullable) and
  `reminders_enabled`. Defaults are applied **once** when inserting a missing
  client checklist step; applying a template again preserves client records.
- Portfolio overview is limited to 5,000 rows and uses the existing
  `firm_client_onboarding_steps` RLS policies. Only independently
  accessible client organisations are represented.

## Reminders
`private.firm_onboarding_due_notifications()` runs daily using pg_cron
(`linkbooks-firm-onboarding-reminders`, `25 1 * * *`, UTC).
It inserts **only in-app** `action_notifications`; no email/SMS,
external client portal or third-party delivery.

Recipients must still be active members of the firm and client organisation,
and the firm/client link must remain active. Only uncompleted steps with an
assignee, due date and enabled reminders are candidates. Notices are scheduled
for 3 days before, on the due date and every 7 days overdue for up to 28 days.
The `(company_id,recipient_user_id,event_key)` unique constraint prevents
duplicates for one date. Event keys reference the firm and checklist task;
target path is `/firm`.

## Security
- Existing firm/client RLS and MFA enforcement remain active on step records.
- Database triggers validate assignee access, scoped prerequisites, cycles and
  completion order even if an older frontend sends an update.
- The reminder function is in the private schema, `SECURITY DEFINER` for
  the scheduled job, has an empty search path and is revoked from
  `public`, `anon` and `authenticated`.
- Server mutations require authenticated firm admin + active client access;
  all updates use optimistic `version` matching.

## Verification
- Run `supabase/tests/firm_onboarding_automation.sql` against a migrated,
  isolated testing environment. It rolls back synthetic companies, users,
  checklists and notifications.
- Unit-test schema and pure due/dependency calculations:
  `npm test -- src/lib/firm/firm-workflows.functions.test.ts
  src/lib/firm/onboarding-insights.test.ts`
- Verify `npm run typecheck`, `npm run lint` and `npm run build` locally.
- Manually test two firms, two authorized users, viewer/admin access, restricted
  client records, blocked prerequisites, completion/reopen, default due dates,
  daily reminder opt-out, notification bell, local-time display and mobile layout.
- GitHub CI workflows are **not run** per user instruction.

## Operational limitations
The default reminder schedule uses UTC and the existing in-app notification
system. It is not a guaranteed delivery service. Reminders for steps older than
28 days are not generated by the scheduled function; such overdue work remains
visible on the onboarding dashboard until completed. The overview is scoped to
the current user's authorized client records, not necessarily the whole firm.
